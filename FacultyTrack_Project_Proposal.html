Introduction & Objectives
FacultyTrack · 2026
Section 01
Introduction

Modern university campuses face a persistent challenge: students and administrative staff have no reliable way to know whether a faculty member is available, where they are located, or when they can be approached. Traditional notice boards, phone calls, and manual room visits are inefficient and time-consuming.

FacultyTrack addresses this problem by providing a centralized, real-time digital platform that tracks faculty availability, enables students to request meeting schedules, and allows faculty to manage their own presence status — all accessible from any device through a web browser, with no installation required.

Section 02
Problem Statement

In a typical university environment, the following problems are consistently observed:

🕐
Wasted Time

Students visit faculty offices only to find them absent or occupied, wasting valuable academic time.

📡
No Availability Signal

Faculty have no streamlined way to communicate their current availability or location to students.

📋
No Centralized Dashboard

Administrative staff lack a single view to monitor faculty presence across the entire campus.

📩
Informal Appointment Booking

Meeting requests are handled via phone or text with no tracking, confirmation, or accountability.

Section 03
Objectives
1
Real-Time Visibility

Provide live faculty availability status and campus location to all stakeholders.

2
Digital Meeting Requests

Enable students to send, track, and manage scheduled meeting requests with faculty.

3
Self-Managed Status

Allow faculty to update their own availability status and location instantly from any device.

4
Admin Control Panel

Give administrators tools to manage users, monitor activity, and operate QR-based check-ins.

5
Secure Role-Based Access

Enforce appropriate access controls for admins, faculty, and students at both UI and database levels.

Section 05
System Features
5.1  Faculty Directory

A real-time grid dashboard displaying all faculty members with live status, location, and last-seen timestamps. Students and staff can search by name or department and filter by any status value. A statistics panel shows on-campus percentage, available count, and occupancy breakdown at a glance.

5.2  Real-Time Status Updates

Faculty can update their own status, location, and note instantly. Status options include: Available, In Meeting, In Class, In Lab, On Break, Busy, Away, Off Campus, On Leave, and Offline. Updates are reflected across all connected clients within milliseconds via WebSocket subscriptions, with every change logged in the activity audit trail.

5.3  QR Code Check-In System

Each faculty member has a unique QR code encoding their ID and name. Admins operate a camera-based QR scanner terminal; scanning a faculty QR code automatically sets their status to "Available" and records a timestamped check-in event in the activity log.

5.4  Schedule Request System

Students can browse the live faculty list, select a member, and submit a meeting request specifying subject, preferred date and time, duration (15–60 min), and an optional message. Faculty can accept or decline requests with an optional response note. Students can cancel pending requests. Full history is visible to both parties with status tracking.

5.5  In-App Notification System

Real-time notifications are delivered instantly without page refresh via Supabase Realtime. A bell icon in the top navigation bar shows an unread count badge. The sidebar navigation also displays a badge on the schedule page when new unread activity exists. Clicking a notification marks it as read and navigates directly to the relevant page.

📣  Notification triggers: Student submits request → Faculty notified · Faculty accepts → Student notified · Faculty declines → Student notified · Student cancels → Faculty notified · Student submits a thesis/project PDF → Faculty notified · Faculty approves, rejects or requests a revision → Student notified.

5.6  Thesis & Project Submission System

Students submit their thesis or project report as a PDF addressed to one specific faculty member, together with a title, document type, and an abstract or note. Files are validated on the client and again by the storage bucket — PDF only, maximum 15 MB — and are stored in a private bucket, reachable only through short-lived signed URLs rather than a permanent public link.

The reviewing faculty member opens the PDF and records a decision: Approve or Deny. Before approving they may correct the submission's title and document type, which the interface surfaces as Edit & Approve — one action that saves the correction and the approval together. Written feedback is mandatory for a denial, so the student always receives a reason.

A resubmission is stored as a new version row rather than an edit of the original, so the complete revision history is preserved. Both the student and the faculty member see every version, its status, its feedback and its timestamps — giving each side a per-student submission activity log. Faculty additionally get a By Student view that rolls up all of a student's works, upload counts and outcomes in one place.

📄  Status lifecycle: submitted → under review → approved · or → denied → student resubmits as v2 → review repeats. Every transition is timestamped, notified to the other party in real time, and recorded as its own version row.

5.7  Admin Panel

A comprehensive control panel with five modules: User Management (create, edit, delete accounts, reset passwords, upload photos), QR Scanner Terminal (camera-based check-in), Submissions (oversight of every student submission and its review outcome), Activity Log (full audit of check-ins and status changes), and System Settings (campus configuration).

Section 07
System Architecture

FacultyTrack follows a client-server architecture where the React frontend communicates directly with Supabase via its JavaScript SDK. There is no custom backend server — Supabase's auto-generated REST API and WebSocket layer serve all data needs, while Row-Level Security policies enforce authorization at the database level.

Section 09
How It Works — User Flows
9.1  Faculty Check-In Flow
1
Faculty arrives on campus

Faculty opens FacultyTrack on their device and navigates to the QR Check-In page.

2
QR code displayed

Their unique QR code (containing staff ID and name) is displayed on screen.

3
Admin scans the code

Admin uses the QR Scanner terminal (camera-based) to scan the faculty's QR code.

4
Status updated automatically

The system sets the faculty's status to "Available", logs a check-in event, and instantly updates the dashboard for all connected users.

9.2  Student Meeting Request Flow
1
Student browses faculty directory

Student logs in with Student ID and opens "Request Schedule". They browse faculty with live status indicators.

2
Student submits a request

Selects a faculty member and fills in subject, preferred date, time, duration, and an optional message, then submits.

3
Faculty receives instant notification

A real-time notification appears on the faculty's bell icon with a sidebar badge on "Schedule Requests".

4
Faculty responds

Faculty opens the request, reviews the details, and accepts or declines with an optional note.

5
Student notified of response

The student receives an instant notification showing the faculty's decision and any note provided.

9.3  Faculty Status Self-Update Flow
1
Faculty opens My Profile

Faculty logs in and navigates to their profile page where their current status is displayed.

2
Status updated

Selects a new status, enters a location (e.g. "Room 402") and an optional note, then clicks Update.

3
Instant dashboard update

The change is immediately visible to all connected users on the Faculty Directory dashboard.

9.4  Thesis / Project Submission & Review Flow
1
Student prepares the submission

Student opens "My Submissions", chooses Thesis or Project Report, enters a title and abstract, and selects the faculty member who will review it.

2
PDF uploaded to private storage

The file is checked for type and size, then uploaded into a private bucket under a path owned by that student. A database row records the metadata and sets the status to submitted.

3
Faculty notified in real time

A notification appears on the reviewing faculty member's bell icon, with a badge on the "Submissions" sidebar item. No other faculty member can see the submission.

4
Faculty reads the PDF

Clicking "Start Review" moves the status to under review and notifies the student. Opening the PDF generates a short-lived signed URL valid for five minutes.

5
Faculty records a decision

In the review dialog the faculty member may correct the title and type, writes feedback, and chooses Approve or Deny. Correcting a field turns the approve button into Edit & Approve. Feedback is required to deny.

6
Student notified — and may revise

The student is notified instantly and reads the feedback. If it was denied, "Resubmit" pre-fills the form and the corrected PDF is stored as version 2, linked to the original so the whole history remains visible to both sides.

Section 10
Security Model
LayerMechanismWhat it protects
AuthenticationSupabase Auth · JWT tokensAll routes require a valid session. Unauthenticated users are redirected to login.
Route GuardsRequireAuth HOC with role checkAdmin-only and staff-only pages redirect unauthorized users to dashboard.
Database RLSPostgreSQL Row-Level SecurityEvery table has policies — users can only read/write rows they are authorized for.
Student Insert ControlRLS WITH CHECK clauseStudents can only insert schedule requests and submissions where student_id matches their own UID.
Review IntegrityRLS UPDATE policy excludes studentsOnly the assigned faculty member (or an admin) can change a submission's status or feedback — a student cannot approve or reopen their own work.
Submission PrivacyRLS SELECT policyA submission row is visible only to its author, the faculty member it was sent to, and admins. No other student or faculty member can read it.
Private File StorageNon-public bucket + storage policies + signed URLsThesis PDFs have no permanent public URL. Uploads are restricted to a folder owned by the uploading student, and reads are limited to the owner, the assigned reviewer and admins.
Upload ValidationClient checks + bucket constraintsOnly application/pdf files up to 15 MB are accepted; the bucket re-enforces both limits server-side.
Notification PrivacyRLS SELECT policyUsers can only read notifications addressed to their own user_id.
Secrets ManagementVercel Environment VariablesAPI keys never committed to the repository; injected at build time.

🔒  Authorization is enforced at the database level via RLS, not just in the UI. This means even if a user manually crafts an API request, they cannot access data outside their permitted scope.

Section 11
Deployment

The application is deployed on Vercel with continuous deployment from the GitHub main branch. Every push to main triggers an automatic rebuild and global CDN deployment. Environment variables are configured securely in Vercel's project settings and are never exposed in the source repository.

Future Scope
🤖
AI Chat Assistant

An embedded assistant powered by Claude (Anthropic) for natural language faculty queries, meeting booking, and status updates.

📧
Email & SMS Alerts

Push schedule updates beyond the web via SendGrid or Twilio for SMS notifications.

📅
Calendar Integration

Export accepted meetings directly to Google Calendar or Microsoft Outlook.

📱
Mobile Application

React Native app for Android and iOS using the same Supabase backend.

🔑
Stronger Student Credentials

Student accounts are currently provisioned with the Student ID as the initial password for fast classroom onboarding. A forced password change on first login, or university SSO, is the next step — now that private thesis documents are stored, credential strength matters more than convenience.

🔍
Plagiarism & Similarity Check

Automated similarity scoring on submitted PDFs, surfaced to the reviewing faculty member alongside the document.

✍️
In-Browser PDF Annotation

Let faculty mark up the PDF itself — highlights and margin comments — instead of writing feedback separately from the document.

📊
Submission Analytics

Departmental dashboards showing submission volume, approval rates, average revision counts and review turnaround time.
